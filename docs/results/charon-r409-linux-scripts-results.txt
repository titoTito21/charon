Charon r409: the Linux post-install accessibility scripts, run for real
=======================================================================
Date: 2026-11-23. Source tree: work/charon-src-r395. Nothing was released, no EFI binary was rebuilt.

The r408 notes said "Linux desktop scripts syntax-only". This round ran them. Test machines:
VMware Workstation, the official cloud images of Debian 13.8 (debian-13-generic-amd64.qcow2),
Ubuntu 26.04.1 (ubuntu-26.04-server-cloudimg-amd64.img), Arch (Arch-Linux-x86_64-cloudimg.qcow2)
and Fedora 45 (Fedora-Cloud-Base-Generic-45-1.4.x86_64.qcow2), checksums verified, 4 CPUs, 4 GB,
UEFI, HD audio, NAT; harness work/charon-r409-vm/vm.py (snapshot "pristine" before every run).
WSL 2 and Docker do not work on this host (no "Virtual Machine Platform"), so no containers.
The scripts were run exactly as the first start of a ready image runs them
(firstboot.sh setup CONSOLE GUI READERS LOGIN DESKTOPS DUAL, then firstboot.sh done).
Nobody listened: "speaks" below means measured from outside - the reader's process is there, the
sound server or the reader holds /dev/snd, the PCM device is RUNNING while spd-say or Fenrir's
sound command plays, the synthesizer's log says "Audio output initialized". Audible quality is
not verified.

NOT run (still unproven end to end, see the last section): the Debian installer (preseed,
in-target chroot), the Ubuntu installer (autoinstall, curtin in-target chroot), Charon itself
writing an image and its cloud-init seed, real hardware, GNOME, KDE Plasma, MATE, Cinnamon, LXQt.


(Line numbers of speech.sh below are those of the state in which most of the runs were made;
the last fixes of the day - the sound-server cookie and root's ALSA default - moved everything
after line 830 down by about 30 lines. Search for the names given.)

1. The four reported bugs: root cause and fix
---------------------------------------------
The r408 scripts were run unchanged on pristine Arch and Debian for comparison
(firstboot.sh setup fenrir cthulhu orca,cthulhu,speakup,fenrir,emacspeak graphical
i3-wm,lightdm,lightdm-gtk-greeter no).

Bug 1, Cthulhu "not installed".
  Arch, r408: installed (cthulhu 2026.10.31-7 from the Stormux repository). The user's guess
    "the AUR is not enabled" does not apply to Cthulhu: the AUR has no cthulhu package at all
    (https://aur.archlinux.org/rpc/v5/info?arg[]=cthulhu returns nothing); Stormux's own package
    repository has it (https://packages.stormux.org/x86_64/stormux.db).
  Debian, r408: NOT there after the first start. speech.sh only wrote and enabled
    charon-cthulhu-build.service ("cthulhu is built at the first start with the network") and
    never started it, although a ready image's first start IS a running system with a network.
    Measured: `command -v cthulhu` empty after firstboot; built only during the second start
    (2 min 9 s CPU), silently, and used only from the sign-in after that. In the i3 session of
    that second start Orca ran, not Cthulhu.
  Second cause, every system: the autostart entry tested `pgrep -x orca` for ANY user. The
    sign-in screen's Orca (user lightdm) is still alive while the session starts, so the entry
    concluded "a reader is running" and started none (measured on Debian: i3 session with no
    reader at all).
  Fix: speech.sh:305-345 the build service is started at once on a running system (log
    /var/lib/charon/cthulhu-build.log, failures written there and retried at every start);
    speech.sh:276-303 one script /usr/local/bin/charon-reader starts the chosen reader, looking
    at this user's processes only (pgrep -U).
  Verified r409: Debian 13 - built from source in the first start, /usr/local/bin/cthulhu,
    cthulhu-braille, cthulhu-input-helper; `cthulhu --version` = 2026.10.31-master; running as
    the test user in the i3 session after the restart. Arch - /usr/bin/cthulhu from Stormux,
    running in the i3 session.

Bug 2, "i33" = I38 "not installed".
  I38 is not a package: Stormux's package "i38" is an empty meta package (depends on brave-bin,
  thunderbird, mumble, cthulhu, fenrir ...; its .INSTALL only prints "git clone
  https://git.stormux.org/storm/I38; ./i38.sh"). r408 did clone it and run "i38.sh -D", and the
  file ~/.config/i3/config was written on Arch and Debian. What was broken around it:
  - Debian and Ubuntu: i3-wm brings dex. With dex installed I38 does not start the reader from
    its configuration but writes an autostart entry with `dex -t ~/.config/autostart -c READER`,
    which failed: "Target directory does not exist: /home/USER/.config/autostart"
    (/var/lib/charon/i38.log). I38 therefore started no reader at all.
  - Debian: no sound server was installed with i3 (Arch got PipeWire from firstboot.sh, Debian
    and Ubuntu nothing). Measured in the r408 i3 session: the user's speech-dispatcher logged
    "ALSA ERROR: Cannot open audio device default (Permission denied)", "Opening audio failed",
    spd-say hung (timeout): the desktop was silent.
  - Debian and Ubuntu: `dconf update` was skipped silently because dconf-cli is not installed
    with i3 or Xfce, while /etc/dconf/profile/user already named the database: every program
    printed "unable to open file '/etc/dconf/db/local'" and none of Charon's desktop defaults
    existed (the same would silence GNOME/MATE/Cinnamon's own start of Orca).
  - With Stormux's i38lock installed, I38's default locks the screen two seconds after i3
    starts (made for Stormux's automatic sign-in): a second password prompt right after LightDM.
  Fix: speech.sh:135-160 (requirements in one transaction, optional ones one by one, PipeWire:
    pipewire-audio on Debian/Ubuntu, pipewire-pulse pipewire-alsa wireplumber on Arch, i38lock
    from Stormux on Arch), :205-213 (dconf-cli / dconf installed, result checked, the profile
    removed and a problem reported when the database cannot be made), :410-460 charon-i38
    (mkdir ~/.config/autostart first; output kept in /var/lib/charon/i38.log; the result checked;
    the reader started only through charon-reader; the lock at start removed, the lock key kept).
  Verified r409: Debian 13 and Arch - config written, after a restart i3 runs with Cthulhu,
    speech-dispatcher, PipeWire with the sink "HD Audio Controller Analog Stereo".

Bug 3, Fenrir without sounds.
  Arch (Stormux's Fenrir, now written in Go, settings.toml): [presentation.sound] driver="pulse"
    and Charon set PULSE_SERVER to a link that exists only while a user's sound server runs.
    A console-only system, or the console before anybody signs in, has none. Measured on r408:
    "sound unavailable or incomplete ... connect sound server: dial unix /run/pulse/native: no
    such file or directory", Fenrir holds no /dev/snd descriptor. Fenrir's README: "Failures
    never select a different audio driver".
  Debian/Ubuntu (Python Fenrir 2025.0.x, settings.conf): sounds are played with sox ("play").
    sox was installed but (a) sox's PulseAudio driver is called "pulseaudio", (b) a "play" that
    started while the desktop's PipeWire was looking for the card took the card (through dmix),
    hung in state PREPARED for minutes and left PipeWire with no sink at all - measured: the
    whole i3 session silent, `wpctl status` without sinks, two stuck "play" processes.
  Fix: speech.sh:509-568 Fenrir's packages and its sound settings (enabled, theme default,
    the generic driver through /usr/local/bin/charon-fenrir-play with a 15 s limit: the signed-in
    user's sound server OR the card, never both); speech.sh:826-915 charon-audio-share: the link
    is made only when a sound server really holds the card (servercard), every console reader
    waits for that before it starts when a session exists (ExecStartPre "sound", up to 15 s),
    and the Go Fenrir's driver is written as "pulse" or "alsa" at each start; HOME=/root for
    the reader services so that root's ALSA default is found.
  Verified r409: Fedora and Arch at the console - driver "alsa", Fenrir holds /dev/snd; Arch
    and Debian with a session - driver "pulse", Fenrir listed as a PipeWire client
    ("/usr/bin/fenrir" in `pactl list short clients`), charon-fenrir-play rc=0 with the card
    RUNNING, no stuck play process, the session's sink present.

Bug 4, Emacspeak.
  Arch: not in the repositories; r408 ran `pacman -S emacspeak emacspeak-espeak-server`, which
    cannot work ("charon: emacspeak could not be installed", measured). Here the user's guess is
    right: only the AUR has it (emacspeak 60.0-1, maintained by Storm Dragon), and it depends on
    tclx, also AUR only (tclx 8.6.3-4, needs exactly tcl=8.6.16-1, which Arch has today).
  Fix: speech.sh:98-133 aur(): an unprivileged account charon-build (no password, no shell)
    clones https://aur.archlinux.org/NAME.git and runs makepkg; root installs the recipe's
    dependencies (repositories first, AUR-only ones the same way) and then the built package
    with pacman -U. speech.sh:619-650: Debian/Ubuntu emacs-nox + emacspeak +
    emacspeak-espeak-server + sox; Fedora emacspeak (packaged, 60.0); Arch aur emacspeak; then
    a check that the eSpeak speech server (tclespeak.so) and tclsh really exist.
  Verified r409: Arch - tclx 8.6.3-4 and emacspeak 60.0-1 built and installed,
    /usr/lib/emacspeak/tclespeak.so; Debian, Ubuntu - emacspeak 53.0 with
    /usr/lib/emacspeak/tclespeak.so; Fedora - /usr/lib64/emacspeak/servers/native-espeak/tclespeak.so.
    NOT verified: Emacspeak actually speaking on console 1 (needs a person at the console).

Failures are no longer silent: every package manager's output goes to
/var/lib/charon/speech-packages.log; whatever could not be done is collected in
/var/lib/charon/speech.problems, spoken at the end of the first start (firstboot.sh:193-202,
speech.sh:975-989) and printed at every console sign-in (/etc/profile.d/charon-problems.sh)
until a later run succeeds.

----------------------------------------------
https://stormux.org says: "You can grab the latest images for the Raspberry Pi 4, Raspberry Pi 5,
and x86_64 systems from https://stormux.org/downloads". The listing has
stormux-x86_64-2026-11-01.iso, 2 043 084 800 bytes, and stormux-x86_64-2026-11-01.iso.sha1sum
(3b79025b1c2fab1deb74a3e67b89771cf27bc7b1). Downloaded and checked: the SHA-1 matches. It is an
archiso image: \EFI\BOOT\BOOTx64.EFI (systemd-boot), default entry "Stormux Accessible Linux
(x86_64, UEFI) with speech" (accessibility=on, archisolabel=STORMUX_X64); its root image enables
stormux-speech.service, which starts Fenrir, signs root in on console 1 and holds
/usr/local/bin/install-stormux and configure-stormux. So: bootable through Charon's existing ISO
path, speaks in the live system (by its contents; it was not booted or listened to).
Added in CharonWsInstall3.h:52-60 (line numbers of the headers are those of 2026-11-23, late
morning; another agent was editing the same headers), pattern of the Slint entry: Speech::installer ("speaks in the
installer"), Way::iso, 1950 megabytes, a spoken note. The address names a dated file: a new
Stormux image needs a new address. As for the other entries of this group Charon does not check
a checksum of ISO images. From a RAM disk the image must find the label STORMUX_X64 itself:
the existing warning of RunIso applies; a USB stick is the safe way.
"Stormux-style" Arch also exists now: the Arch ready image with Fenrir, Cthulhu and "i3 with I38"
gets Stormux's repository, fenrir, cthulhu and i38lock (section 1).

8a. The network chosen in Charon (new: src/linux/network.sh)
-----------------------------------------------------------
How Charon connects today (src/efi/CharonWsNet.h): Ethernet or Wi-Fi through the firmware's
drivers, DHCP only; Wi-Fi WPA2-PSK through the firmware's supplicant; enterprise networks are
refused ("Sieci firmowe z logowaniem 802.1X nie są obsługiwane"). The passphrase is typed into a
static buffer and wiped (memset) as soon as the firmware has taken it: it is NOT kept anywhere,
so today nothing could hand it to an installed system. No install path gets any network
configuration from Charon: Debian's preseed says netcfg/choose_interface auto, Ubuntu's and
Arch's kernel lines say ip=dhcp / ip=:::::eth0:dhcp, the ready images' seed has no
network-config (cloud-init's default: DHCP on the wired adapter).

Script side, done and tested: network.sh (300 lines; compiled in as networkScript, written to
\EFI\HAK\network.sh of a ready image and copied by its first start, CharonWsInstall3.h:301,441).
  network.sh apply   reads /var/lib/charon/network.conf (mode 600, root):
      CHARON_NET_TYPE ethernet|wifi      CHARON_NET_MAC aa:bb:cc:dd:ee:ff (may be empty)
      CHARON_NET_METHOD dhcp|static      CHARON_NET_ADDRESS 192.168.1.10/24
      CHARON_NET_GATEWAY                 CHARON_NET_DNS a,b        CHARON_NET_PROXY http://host:port
      CHARON_WIFI_SSID                   CHARON_WIFI_SECURITY open|wpa-psk|enterprise
      CHARON_WIFI_PSK (8..63 characters, or 64 hex digits)        CHARON_WIFI_COUNTRY PL, US ...
    and writes the connection for the network manager the system has:
      NetworkManager - a keyfile /etc/NetworkManager/system-connections/charon-TYPE.nmconnection,
        600 root, autoconnect (https://networkmanager.dev/docs/api/latest/nm-settings-keyfile.html);
      netplan - /etc/netplan/90-charon.yaml, 600 (https://netplan.readthedocs.io/en/stable/netplan-yaml/),
        checked with `netplan generate` before `netplan apply`;
      systemd-networkd - /etc/systemd/network/05-charon.network, and for Wi-Fi iwd's
        /var/lib/iwd/SSID.psk, 600 (https://iwd.wiki.kernel.org/networkconfigurationsettings).
    Wi-Fi: the WPA2 key is computed from the passphrase (PBKDF2) and stored instead of it; the
    passphrase is removed from network.conf after a successful apply and from the EFI partition
    by firstboot.sh; it is written to no log. The regulatory domain goes to
    /etc/modprobe.d/charon-regdom.conf (cfg80211 ieee80211_regdom), netplan's regulatory-domain
    and iwd's Country. Missing pieces are installed when a network is there (wpasupplicant / iwd /
    NetworkManager-wifi, iw, the adapters' firmware: Debian firmware-iwlwifi, firmware-realtek,
    firmware-atheros, firmware-brcm80211, firmware-misc-nonfree with the component
    non-free-firmware switched on; Ubuntu, Arch, Fedora linux-firmware). What cannot be done yet
    is a spoken/printed problem and is tried again at every start (charon-network.service).
    Enterprise Wi-Fi: refused with a message, exit 3, nothing written (for the administrator layer).
  network.sh wait N  a default route and a name server that answers.
  firstboot.sh:102-126: apply, then wait - six seconds, then up to five minutes with a double
    tone every ten seconds and a sentence (spoken only when a synthesizer is already installed) -
    before any package is fetched; the old retry at the next start stays.
Tested for real (VMs):
  - Ethernet with DHCP, bound to the adapter's address: applied on Fedora (NetworkManager),
    Debian (netplan) and Arch (systemd-networkd); the network stayed usable.
  - Wi-Fi with WPA2 on the kernel's simulated radios (mac80211_hwsim) against a hostapd access
    point whose name is `Dom Kowalskich "5G" ąę` and whose passphrase holds quotes, a dollar sign
    and a backslash: Debian 13 (netplan, wpa_supplicant) - connected in 5 s, the access point
    logged AP-STA-CONNECTED and EAPOL-4WAY-HS-COMPLETED; Fedora 45 (NetworkManager) - the access
    point logged "WPA: pairwise key handshake completed (RSN)", NetworkManager's supplicant state
    "completed" (then waiting for an address: the test access point has no DHCP server).
  - Files only (the system's own tool accepted them): a static address on Fedora (nmcli reads back
    manual 192.168.50.10/24, gateway, two name servers) and Debian (netplan generate; the
    generated networkd file has Address, Gateway, DNS); open Wi-Fi on all three; on Arch the iwd
    file (name "=446f6d...psk" for a name with other characters, PreSharedKey equal to the
    independently computed key). The key stored by NetworkManager, netplan/wpa_supplicant and
    iwd equals PBKDF2(passphrase, name) computed separately. Refusals: enterprise rc 3, a short
    passphrase rc 2, a static address without prefix and gateway rc 2.
  - First start with a network.conf (Ethernet, DHCP): the Debian Xfce run of section 8.
NOT tested: Wi-Fi with iwd actually associating (iwd took both simulated radios; file-validated
only); Ubuntu (same netplan as Debian, not run); a real Wi-Fi adapter; a proxy; the wait when
there really is no network; a desktop's NetworkManager taking over from netplan/networkd after
the desktop is installed (on Debian and Ubuntu images the connection stays with netplan and
systemd-networkd, where NetworkManager shows the adapter as unmanaged).
The hard limit, stated plainly: the ready images contain no wpa_supplicant, no iwd and no Wi-Fi
firmware (checked on all four images). On a machine with Wi-Fi only, the first start therefore
has no network to fetch them with; network.sh says so ("connect a network cable once") and
finishes at the first start that has a network. Only Charon putting those packages onto the
disk, or an image that has them, removes this limit.

WHAT THE EFI SIDE STILL HAS TO DO (nothing of this was changed; CharonWsNet.h and the generators
are being edited by others):
  1. Keep what the user chose: adapter address, Ethernet or Wi-Fi, the network's name, security,
     and the passphrase (today wiped in WifiJoin) - in memory only, in a buffer that is cleared
     after the answer files are written; never in the settings record, a saved answer set or a
     trace. The country from Charon's language/region setting.
  2. Ready images: write \EFI\HAK\network.conf (the fields above) beside network.sh; it must be on
     the list of files that are never copied to other media (the \EFI\HAK exclusion list).
  3. Debian (https://www.debian.org/releases/trixie/example-preseed.txt, appendix B.4.2): in the
     preseed that is already inside the initrd - d-i netcfg/choose_interface select IFACE,
     d-i netcfg/wireless_essid string NAME, d-i netcfg/wireless_security_type select wpa,
     d-i netcfg/wireless_wpa string PASSPHRASE; for a static address netcfg/disable_autoconfig
     boolean true, netcfg/get_ipaddress, netcfg/get_netmask, netcfg/get_gateway,
     netcfg/get_nameservers, netcfg/confirm_static boolean true. Checked: the netboot installer
     Charon starts does contain wpasupplicant-udeb and nic-wireless-modules (MANIFEST.udebs of
     trixie, netboot and netboot/gtk) but no firmware (manual 6.4), so Wi-Fi works there only
     with adapters that need none, unless Debian's firmware.cpio.gz (497 MB,
     https://cdimage.debian.org/cdimage/firmware/trixie/current/) is appended to the initrd.
     The installer itself saves the connection it used into the installed system.
  4. Ubuntu (https://canonical-subiquity.readthedocs-hosted.com/en/latest/reference/autoinstall-reference.html,
     "network": netplan version 2, wifis / access-points / password; it is applied in the
     installer and copied to the installed system). But Charon starts Ubuntu's installer from
     the network (ip=dhcp iso-url=...): the initial RAM disk fetches the ISO before any Wi-Fi
     can exist, so this path needs a cable; Wi-Fi would need the ISO on a disk or stick.
  5. Arch started from the network: the same - the initial RAM disk fetches the system over a
     cable (ip=...); once it runs, iwd is there (iwctl --passphrase PASS station wlan0 connect
     NAME, or a file /var/lib/iwd/NAME.psk as network.sh writes it).
  6. Fedora: Charon uses no kickstart; the ready image is served by network.conf (item 2).
