2. The answer store held 48 keys of 159 bytes; generator buffers were 8-16 KB
------------------------------------------------------------------------------
Root cause (CharonWsAsk.h as it was). maxAnswers=48, valueUnits=160. Slot() returned the LAST slot for
a 49th key (the new answer silently overwrote another key's value); Put cut a value at 159 bytes; the
check-box join stopped at 160 bytes with a bare "break" (checked boxes dropped); the typed-text
conversion cut at 159 bytes. Nothing was said in any of these cases. Buffers: preseed 12000, Ubuntu
user-data 8000, image user-data 9000, Autounattend.xml 16000, CHARONPC.CFG 2048 (CfgLine cut silently),
two 400-byte Windows command lines whose overflow flag nobody read.

Change.
  Store (CharonWsAsk.h:22-48, :60-120): 384 keys; values under 512 bytes in the key's own slot, longer
  ones (under 4096 bytes) in one of 32 long slots, chosen by Put itself. Static storage, about 330 KB
  (.bss), never on the stack. Put returns false and stores NOTHING when there is no room (385th key,
  33rd long value, 4096 bytes or more): the old value stays, Overflow()/LostKey() remember it.
  ask::Complete() says by voice which answer could not be kept; ask::Keep() (used by Run for every typed
  or chosen answer) says "This answer did not fit..." and the question is asked again. Run: the
  index array is static (was 384 bytes x 8 on the stack after the enlargement), a table longer than
  the store is refused aloud, defaults that do not fit stop the dialogue with Complete(); a typed
  answer may have 255 characters (was 79), check boxes 64 (was 24); a stored value too long for the
  typing line is kept unless something is typed, instead of being cut by Enter (:264-270).
  Callers: install::Classic stops before anything is started when !ask::Complete() (CharonWsInstall2.h:815);
  RunImage checks it and makes a trial run of the generator BEFORE a disk is chosen (CharonWsInstall3.h:343-348;
  the configuration used to be generated only after the image was on the disk).
  Buffers, all static: preseed 48000 (CharonWsInstall.h:481), Ubuntu user-data 32000 (CharonWsInstall2.h:155),
  Autounattend.xml 64000 (:651), image user-data 32000 (CharonWsInstall3.h:401), CHARONPC.CFG 8192
  (CharonWsDosSystem.h:464). An overflow is now said in its own words (install::AnswersDoNotFit,
  CharonWsInstall.h:31) and nothing is started; CfgLine no longer writes a cut line (CfgOverflow,
  CharonWsDosSystem.h:322-332, said in MakeProfile); the two command lines pass their overflow on
  (CharonWsInstall2.h:502, :509).
  Places that assumed the old sizes: only inside CharonWsAsk.h (Slot, Run); no other file used
  maxAnswers, valueUnits or ask::A(). Bounded helper buffers left as they are, with the reason: ReaderArguments
  and ReaderPackages (200 bytes) and the desktop package list (400) are filled from fixed tables (longest
  today 238 bytes); they cut silently if a table ever outgrows them - to be turned into Text with an
  overflow flag when the tables become generated (spec 3.1).

How verified. RAN AND PASSED on the host (harness command "store", 23 checks): 384 keys stored and read
back; the 385th refused, recorded, said by Complete(); lengths 159, 511, 512, 4095 bytes uncut, 4096
refused with the old value kept; 32 long values, the 33rd refused; Clear; Has() on a long check-box
value; a key copied from another key and onto itself; the real ask::Run with scripted keys: a typed
answer of 750 bytes with no long slot left is reported by voice and asked again, then stored; a table
whose defaults do not fit is refused by voice; Text reports overflow. The declared buffer sizes are
read from the sources and compared with the plan, and the largest test output uses under a quarter
of each. COMPILED ONLY: in CHARON.EFI. NOT VERIFIED: in a VM; the size of .bss in the firmware image was
not measured separately (the image built and its size did not grow by the 330 KB: zero-filled data).

What remains. The spec's new question kinds (number, list, address, file) and the "long" flag are not
implemented; the store is ready for them. Secret answers are still limited to 79 characters.

5.1 Facts about the copy in memory today (AUDITED: CharonSelfCopy.h, CharonSelfRam.h, BootMenu.h:1603-1607)
  - What is held: every file under \EFI\HAK of the start volume, listed once, 400 menu-loop turns after
    the start, then read 256 KB per turn; the running program as HAKBOOT.EFI when the folder has none.
    Limits: 600 files, 64 folders, paths under 200 characters - what exceeds them is skipped WITHOUT a
    word (CharonSelfCopy.h List). Left out: continue.bin, continue-set, installed-by.txt, reader-only,
    windows-iso-url.txt. Since this work: answers\ and plan\ are held too, marked privateItem.
  - When Charon moves: as soon as the copy is complete, in the menu's loop only. From then on its root,
    its "own device" and its image's device are a FAT32 volume in memory. New: images::EnsureInMemory
    (CharonWsImages.h:184-207) finishes the copy and moves at once when an installation asks for a disk
    to erase and Charon's own disk is present - before, that disk was simply missing from the list
    until the background copy had finished, with no word of why (COMPILED ONLY).
  - What is written back, and when: nothing by itself. Settings changed after the move are also written
    to the start medium while it is still mounted (MirrorSettingsToMedium). Charon is written to a disk
    only by: images::CharonOnto (ready image, CharonDOS - right after the image or the partition is
    made, before any restart; with the firmware entries), the cpio a Debian installation carries
    (written by the installer's late_command at its very end), the copy on Windows media (written by
    Install-Charon.ps1 at the first logon), the Ubuntu early/late-commands, "Install Charon on this
    computer".
  - What survives a restart: nothing of the volume in memory. Whatever must survive has to be on a disk
    (or in a UEFI variable) before the restart.
  - For a plan (\EFI\HAK\plan on a disk that is repartitioned) this gives today: the state AS IT WAS
    WHEN CHARON WAS COPIED INTO MEMORY is in memory and is carried back to the new EFI partition by
    images::CharonOnto(esp,true) on the two paths where Charon itself makes the new partition (ready
    image over the whole of its own disk, CharonDOS over the whole of its own disk) - before the first
    restart. Missing for plans and answer sets: (a) a write of the plan state to the volume in memory
    AND to the disk after each change (the copy is a snapshot; a helper like MirrorSettingsToMedium for
    a named file does not exist); (b) on the installer-based paths (Debian, Ubuntu, Windows) the disk
    is repartitioned by the installer after Charon has handed over, so Charon cannot write anything
    "as the first step after the layout is created": the state must travel inside the installer's
    hooks (cpio / media / config set) or the layout must be made by Charon first; (c) the UEFI
    variable pointer of the multi-boot spec; (d) the silent limits above (600 files) must become
    spoken; (e) CharonOnto is usable as the "re-create Charon on a fresh EFI partition" helper before
    the first installer restart (it needs only the volume handle), the firmware entries are

5.3 Windows from the RAM disk: what exists, why it is not automatic, the design (NOT IMPLEMENTED)
  Today (CharonWsRamDisk.h, CharonWsInstall2.h Classic): without media Charon offers "download to a USB
  stick" (then the normal unattended path) or "download to a RAM disk": the ISO from Microsoft is loaded
  into reserved memory and registered with the firmware's EFI_RAM_DISK_PROTOCOL as a virtual CD (the
  firmware publishes it in the ACPI NFIT, so an operating system can still find it); its boot manager
  is started. That is the coordinator's option (a) and it is already the mechanism in the tree. It is
  manual ("you go through Windows Setup yourself, with Narrator") because the ISO is a read-only disc:
  no Autounattend.xml, no \charon folder, no NVDA for the WinPE phase, no write-back of Charon. And it
  has never been proven that Setup finds its sources there (charon-r401-results.txt:53; r402 "NOT
  tested: RAM-disk way"). Memory rule in the code: 9 GB for the image + 3 GB spare free, else the USB
  way is offered first (said). Firmware without the protocol: said, no fallback.
  Design for an automatic RAM-disk installation (to be its own batch; nothing of it was shipped):
    1. Second RAM disk: a small FAT image built in reserved memory and registered as a virtual DISK
       (EFI_VIRTUAL_DISK_GUID) next to the virtual CD, holding Autounattend.xml at its root, the NVDA
       files for the WinPE phase and Charon. Setup looks for Autounattend.xml at the root of removable
       media; whether an NFIT virtual disk is searched and gets a drive letter in WinPE must be measured.
    2. The decisive point: memory does not survive Setup's first restart. Today's answer file runs
       Install-Charon.ps1, the readers and the profile from "%d:\charon" on the MEDIA at the first logon
       - with a RAM disk there is no media any more by then. The files must reach the Windows partition
       during the WinPE phase. The documented way is a configuration set (Microsoft-Windows-Setup
       UseConfigurationSet, $OEM$\$1\... beside the answer file is copied to the system drive); the
       first-logon commands then use %SystemDrive%\Charon. This needs a second form of WindowsAnswers
       (host-testable now) and proof on real Setup.
    3. Fallback when memory is short (never "do it yourself"): a temporary media partition at the end
       of the target disk (split WIM as for the USB stick, CharonWimSplit.h), an answer file that does
       not wipe the disk (creates Windows in the free space before it), and a first-logon step that
       removes the media partition and extends C:. Announced by voice before anything is written. The
       known defect of the self-installer (an empty "Charon" partition stays when a later step fails)
       must not be repeated: delete the partition entry on failure.
    4. Unchanged: BitLocker prevention, reader in WinPE, AutoLogon handling, Charon's hooks.
  Documentation: NOT re-read in this batch (no page was fetched). The statements about the answer-file
  search order, UseConfigurationSet/$OEM$ and NFIT support in Windows Setup are from memory of
  Microsoft's "Windows Setup Automation Overview", the unattend reference and the UEFI specification
  (RAM Disk Protocol) and are to be treated as UNVERIFIED until the batch that implements them reads
  the pages and measures in VMware. Nothing was measured here (no Windows VM was run).
