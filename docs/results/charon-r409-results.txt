Account name of the build computer
----------------------------------
Found during this release: the images built on the build computer held its account name inside absolute
paths - the ELF's path in the PE debug entry of CHARON.EFI, CHARONVOICE.EFI and CHARONDOS.EFI, __FILE__
strings in espeak.tts and rhvoice.tts, debug paths in seven files of the driver pack - and so did logs and
build scripts inside driver-pack-source.zip and four files of charon-source-r394.zip. The r408 checks
looked at text files only, so THE RELEASED r408 PACKAGES (and older ones that hold these files) CONTAIN
THAT NAME; they were not changed.
For r409 (work/scrub-private-r409.py, prepare-release-inputs-r409.py, scan-private-r409.py): in every such
place the account name is replaced by the word "user" - the same number of bytes, the PE checksum corrected
where the image has one, the sha256 lines of the synthesizer manifests set to the changed modules, the
driver pack's MANIFEST.json corrected. Nothing else differs from the build output; the hashes as built and
as released are in release-inputs-r409.json (docs/results in the source tree). The packagers scan every file
of every package, binaries and zip members included, and refuse to pack on a hit.
Consequence for the tests: the smoke checks ran on the trace builds (unchanged files); the release checks
at the end ran on the released files, including the changed synthesizer modules (their checksum is verified
by Charon when a module is loaded).
Not done: a build that does not write such paths in the first place (the build tools are unchanged).

  proven in whole-disk mode only; the free-space and replace modes are compiled only.
