How the pieces work together (as it ran)
  - The answers of each system are captured from the question store into [system.<id>] of the
    plan (the clear password never; its hash does) and put back before that system's generator
    runs, so every generator reads ask::Get as always.
  - Step 0, after the typed word: variable CharonPlan (state "preparing"), new GPT, the EFI
    partition (CharonDOS's partition when CharonDOS is in the plan), a named placeholder per
    system; then FIRST Charon onto the new EFI partition (from its copy in memory, with its answer
    sets when the disk was Charon's own home), the plan file, the entries "Charon" (first) and
    "Charon voice". Nothing is written before the layout and the pre-flight have passed.
  - A ready image: its placeholder is removed, the image's partitions go into exactly that range
    (images::Remap with the range as "the gap"), its own small EFI partition stays inside.
    Because its first-start script looks for the plan on ITS EFI partition, Charon leaves a mark
    there (EFI/HAK/plan/plan.txt, current), fetches the marker the image wrote and removes the
    mark; the image's CIDATA seed partition is removed after its first start is done.
  - Debian's installer: its placeholder is removed, FreeGaps must report exactly one free range
    of 16 MiB or more starting where the range starts (else the step fails before the installer
    is started), then the existing "free space" preseed (biggest_free).
  - Try again: FreeRange also removes whatever a failed attempt left INSIDE the range (never
    anything that lies partly outside), so a half-written image can be written again.
  - Finish: CharonDOS's entry is written only now; Charon's own entries are pointed back at the
    plan's EFI partition (an image's first start registers the copy on the image's partition).

What a plan can hold in this version

An abandoned plan (decided and implemented; COMPILED ONLY)
    A plan ends without its finish step when its file cannot be read and the user says
    "discard" (CharonWsPlan.h Open -> DiscardEverywhere). Rule: (1) every volume that carries a
    plan's files or marks loses them - the plan's EFI partition and the EFI partition of every
    ready image, where the mark is what makes the image's start-up script keep Charon first and
    report to a plan that no longer exists; answer files are overwritten with zeros first;
    (2) the entries "Charon" and "Charon voice" are pointed at the plan's EFI partition when it
    is there and holds Charon - an image's first start had registered the copy on the image's
    own partition; when the plan's partition is not there they are left as they are (a working
    entry is not replaced by a guess); (3) nothing else is touched: installed systems stay,
    unused ranges stay as placeholders named "Charon plan N: ...". "Stop here" on a readable
    plan is not this case: it runs the normal finish step, which already points the entries back.
    Still open: a plan that is readable but whose user simply never comes back (the image's copy

5b. PHASE B2b: Windows in a plan (2026-11-23)
---------------------------------------------
How it is built (CharonWsPlanDialogue.h InstallWindows, CharonWsWinPart.h ProvidePlan)
  - Windows has its own range in the computed layout (64 GB at least for Windows 11); it is a
    placeholder until its step. The installer's temporary media partition is INSIDE that range:
    at the step the range becomes free space, and once the image's size is known Charon makes the
    Windows partition at the start of the range and "Charon Windows media" (FAT32, image + Charon
    + 700 MB) at its end. So the layout accounts for the space, nothing outside the range is
    touched, and the space goes back to Windows: at the first sign-in Charon-MediaCleanup.ps1
    removes the partition and extends C: (moving the recovery partition Setup made to the end of
    the range). The script now looks only at partitions before the end of the removed partition,
    so other systems' partitions behind Windows do not stop it, and it overwrites
    Autounattend.xml (both copies) with zeros before the partition goes.
    (Deviation from the coordinator's wording "reserved as a placeholder": the media partition is
    not a range of its own; it is carved from the Windows range, because its size is known only
    when the server has answered. The summary says so before the typed word.)
  - Setup installs through the existing diskmode=partition branch into the partition by its
    position number, Microsoft reserved partition COUNTED (measured: PartitionID 3 behind EFI
    and MSR in T1, T2, T4), using the plan's EFI partition (with CharonDOS: CharonDOS's).
  - Decision D4: the typed password waits in the step's own file \EFI\HAK\plan\stepN\answers.env on
    the EFI partition (the plan file holds only the hash); plan::Resume overwrites and deletes it
    when the step is done, the finish step at the latest. The answer file itself must lie where
    Setup reads it, on the media partition: overwritten at the first sign-in (above), and after
    the step Charon checks that the partition is gone and removes it itself if not
    (CleanAfterWindows, COMPILED ONLY: Windows removed it in every run).
  - The answer file is the single-system one plus, only when the answer "plan" is set: the time
    zone (TimeZoneElement), and as the LAST first-logon commands hibernation and fast start-up off,
    Install-Charon.ps1 -Mode Manager -Default (Charon first again), -PlanResult done -PlanStep N
    (or failed, with the log's tail), restart. Clock in universal time (clockutc=yes forced) and
    BitLocker prevention (existing answer). \charon\carry is NOT used in a plan (an older copy of
    the plan's files must never be copied over the live ones).
  - Every restart of Setup comes back to Charon (BootNext), which says the step and its start
    number and passes on to \EFI\Microsoft\Boot\bootmgfw.efi (3 pass-throughs per installation).
  - Pre-flight before anything is written: TPM 2.0 through the firmware's TCG2 protocol - when it
    is missing Charon says so and asks whether Setup shall skip the hardware checks (no: the plan
    is not made); the download addresses of ready images and of Windows are asked (HEAD) and a
    dead address refuses the plan. Debian's netboot files are not asked.
  - Finish: Charon is put back as \EFI\BOOT\BOOTX64.EFI (Setup overwrites it); registry, entries,
    Continue target as for the other systems.
  - Versions: the list of the single-system dialogue (Microsoft's own images only). Tiny11 and
    other unofficial images are NOT in plans. Profiles: asked per Windows system (detailed and
    express mode, default "unchanged"); ReviOS and AtlasOS, which need a step done by hand, are
    refused aloud in a plan and replaced by "unchanged".
  - Install-Charon.ps1 -PlanResult: a mounted volume that already holds the plan is used (the

7. Risks
--------
- The guest-restart path was only exercised through power cycles (section 3).
- An image's first start re-registers the entry "Charon" to the copy on the image's own EFI
  partition; until the finish step points it back, Charon runs from that copy. It finds the plan
  through the variable (seen working in T3). If the plan is abandoned in between, the entry
  stays pointing at the image's partition.
- WriteImage repeats RunImage's write sequence; RunImage is being edited by others.
- Removing an image's CIDATA seed after its first start: Debian started again afterwards (T3);
  Ubuntu and Fedora NOT VERIFIED.
- The Windows answer file with the password will lie on the EFI partition from step 0 until its
  step is done (decision D4) once B2b exists; nothing of that kind exists in a B2a plan (Linux
  gets only the password hash; no step files were written in either run).
- Disks without identify data (USB, SCSI, virtio) can never be authorised for an unattended plan.
