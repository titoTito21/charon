======================================================================================================

14:30 and will move). Evidence: work/r409win-evidence. Builds: work/charon-win-r409w4 (CHARON.EFI) and

NOT VERIFIED = neither. Nothing was packaged or released.

Summary
  Windows from a RAM disk: GATED OFF, by measurement (section 2). Windows 11 Setup does not see a firmware RAM disk
    once WinPE runs, whatever the ACPI NFIT says about it. The code that makes such a disk stays in the tree but no
    release path calls it; the old manual "download to a RAM disk" choice for Windows is removed.
  What the user gets instead (section 3): Windows with no stick and nothing to prepare, fully unattended, through a
    temporary partition on the target disk. It works from Charon in memory and onto Charon's own disk.
  Section 4: Install-Charon.ps1 "error 1314". Section 5: Part 2 items. Section 6: the coordinator's four findings.
  Section 7: tests and builds. Section 8: changed files. Section 9: what remains.


1. What the documentation says (read on 2026-11-23; quotes are literal)
-----------------------------------------------------------------------
uefi.org refuses automated fetches; the UEFI and ACPI texts were read from the Wayback Machine's copies of the
official pages. Microsoft Learn and the EDK2 sources were read directly.

1.1 UEFI 2.10, 13.17 RAM Disk Protocol  https://uefi.org/specs/UEFI/2.10/13_Protocols_Media_Access.html
    "The consumer of this protocol is responsible for allocating/freeing memory used by RAM Disk if needed and
    deciding the initial content". Register's RamDiskType: "The GUID can be any of the values defined in RAM Disk,
    or a vendor defined GUID." Nothing in the section about the memory type, ExitBootServices or the NFIT.
    Device path node (10.3.5.9, https://uefi.org/specs/UEFI/2.10_A/10_Protocols_Device_Path_Protocol.html): type 4,
    sub-type 9, 38 bytes; "The Disk Type GUID values used in the RAM Disk device path must match the corresponding
    values in the Address Range Type GUID of the ACPI NFIT table."
    GUIDs: virtual disk 77AB535A-45FC-624B-5560-F7B281D1F96E, virtual CD 3D5ABD30-4175-87CE-6D64-D2ADE523C4BB,
    persistent virtual disk 5CEA02C9-4D07-69D3-269F-4496FBE096F9, persistent virtual CD 08018188-42CD-BB48-100F-
    5387D53DED3D.
1.2 ACPI 6.5, 5.2.26.2 NFIT SPA Range Structure  https://uefi.org/specs/ACPI/6.5/05_ACPI_Software_Programming_Model.html
    "System physical address ranges described as Virtual CD or Virtual Disk shall be described as AddressRangeReserved
    in E820, and EFI Reserved Memory Type in the UEFI GetMemoryMap." The specification defines the regions and
    prescribes nothing about what an operating system does with them.
1.3 EDK2 RamDiskDxe  https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Universal/Disk/RamDiskDxe/
    RamDiskProtocol.c: a disk is put into the NFIT only when its memory is EfiReservedMemoryType, and only when
    EFI_ACPI_TABLE_PROTOCOL and EFI_ACPI_SDT_PROTOCOL were found; Register ignores the result. When no NFIT existed it
    also installs an SSDT with the NVDIMM root device. RamDiskDriver.c: both protocols are looked up in a "ready to
    boot" callback ("If both protocols are produced, publish all the reserved memory type RAM disks to the NVDIMM
    Firmware Interface Table"); before that event nothing is published. OvmfPkgX64.dsc includes RamDiskDxe.inf
    unconditionally and sets PcdInstallAcpiSdtProtocol TRUE.
1.4 Windows and NFIT virtual disks/CDs: NO OFFICIAL STATEMENT FOUND - neither that Windows 10/11, WinPE or Setup
    mounts such a region, nor which driver would, nor anything from Microsoft about UEFI HTTP boot of a Windows ISO.
    (Dell KB 000122099, a vendor page, names scmbus.sys, nvdimm.sys and pmem.sys for real NVDIMM-N modules only.)
1.5 VMware Workstation firmware and EFI_RAM_DISK_PROTOCOL: no official statement found. Measured: section 2.
1.6 Answer file search order  https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-automation-overview
    Eight places, in order: the registry value HKLM\System\Setup\UnattendFile; %WINDIR%\Panther\Unattend (not
    searched when Setup starts from Windows PE); %WINDIR%\Panther; "Removable read/write media in order of drive
    letter, at the root of the drive" ("The name of the answer file must be Autounattend.xml"); removable read-only
    media, the same; "windowsPE and offlineServicing configuration passes: \Sources directory in a Windows
    distribution" (Autounattend.xml); %SYSTEMDRIVE%; the drive Setup runs from. So the root of a FIXED disk's
    partition is not a documented place; \Sources of the distribution is. Charon writes the file to both on a
    partition. Measured (section 3): Setup took the answer file from the temporary partition of the fixed disk.
    Caching: "After the Windows installation is extracted to the hard disk, the answer file is cached to
    %WINDIR%\panther." "Setup removes sensitive data in the cached answer file at the end of each configuration pass."
1.7 Configuration sets and $OEM$
    https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/wsim/distribution-shares-and-configuration-sets-overview
    "If a configuration set is used during Windows Setup, all the contents at the root of the media where the answer
    file exists are copied to the Windows installation." "You can use the $OEM$ folder and subfolders only when you
    are creating configuration sets." $OEM$\$1 = the Windows drive, $OEM$\$$ = %WINDIR%. UseConfigurationSet
    (https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-setup-useconfigurationset):
    default false, windowsPE pass. Consequence for the design of 5.3 in the earlier results file: a configuration
    set at the root of media that also holds the 8 GB of installer files would copy all of it; \sources\$OEM$
    without a configuration set is not documented. Neither is used: the temporary partition is still there at the
    first sign-in, so nothing has to be copied to the Windows drive during the WinPE phase.
1.8 SetupComplete.cmd  https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/add-a-custom-script-to-windows-setup
    "This setting is disabled when using OEM product keys, except on Enterprise editions and Windows Server" - not used.
1.9 WinPE  https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpe-intro : "The base version
    requires only 512MB of memory"; a RAM-disk boot needs "a contiguous portion of physical memory (RAM) which can
    hold the entire Windows PE (WIM) image". Setup's phases
    (https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-installation-process):
    Windows PE phase "3. Configure the disk. 4. Copy the Windows image to the disk. 5. Prepare boot information."
1.10 RunSynchronous  https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-deployment-runsynchronous
    "run ... in the system context in the specialize configuration pass".
1.11 Debian, keyboard-configuration's config script
    https://salsa.debian.org/installer-team/console-setup/-/raw/master/debian/keyboard-configuration.config : outside
    the installer the script asks keyboard-configuration/layout and /variant with "$layout_priority" (critical unless

2. Windows from the RAM disk: measured, and why it is gated off
---------------------------------------------------------------
Machine: VMware Workstation, UEFI, 4.6 GB, Charon on the only (NVMe) disk, the Windows 11 Enterprise 26H2 evaluation
ISO as a SATA CD so that a real Windows Setup can be asked what it sees. Test builds with
CHARON_EXTRA=-DHAK_CHARON_RAMPROBE (never a release build): a 96 MB FAT32 disk in EfiReservedMemoryType memory,
registered with EFI_RAM_DISK_PROTOCOL as a virtual disk, marker files written to it through the firmware's FAT driver.
  a. VMware's firmware HAS the service. Static: EFI64.ROM (LZMA section unpacked) holds RamDiskDxe's file GUID
     28A03FF4-..., the protocol GUID and the string NFIT. Run time (serial trace, RAN AND PASSED): Register succeeded,
     the firmware mounted the volume, both marker files were written ("CHARON ramprobe files=3").
  b. The firmware publishes NOTHING to ACPI for a disk a boot manager registers, also after Charon signalled the
     "ready to boot" event group itself: "CHARON ramdisk NFIT existed=0", not published by firmware. In WinPE:
     no ACPI0012 device, no disk (p-06.png, p-07.png).
  c. Charon then published the range itself, as EDK2 does (an NFIT with one SPA range structure through
     EFI_ACPI_TABLE_PROTOCOL, plus an SSDT with Device(NVDR) _HID "ACPI0012"): both installs returned success,
     "CHARON ramdisk published=1". In WinPE (Windows 11 Setup, cmd version 10.0.26100.9457): the device
     ACPI\ACPI0012 now exists with Service=scmbus (p-08.png, p-09.png) - so Windows read Charon's tables - but
     diskpart still lists only the NVMe disk and the DVD. No disk for the RAM range.
  d. Same again with four ranges in the NFIT, each a copy of the same FAT disk: volatile virtual disk, persistent
     virtual disk, volatile virtual CD, and a plain persistent-memory region (66F0D379-...): diskpart lists none of
     them, and the registry has no SCMLD or SCMBUS children (p-10.png).
  e. WinPE does contain scmbus.sys, pmem.sys, nvdimm.sys and ramdisk.sys (p-07.png): the drivers are there, they do
     not make a disk out of these regions.
Conclusion: after WinPE has left the firmware, a firmware RAM disk does not exist for Windows Setup. boot.wim would
still start (the boot manager reads it through the firmware), and Setup would then stop without its sources. This
is not a matter of the answer file or of memory size; no amount of work inside Charon changes it short of shipping
a Windows storage driver inside boot.wim. NOT measured: QEMU/OVMF (its RamDiskDxe would publish the NFIT itself;
measurement c shows that publication is not what is missing), other Windows versions, real hardware.
State of the code: ramdisk::MakeVolume, Publish and the ACPI helpers (CharonWsRamDisk.h:147-330) are compiled and
called only by the probe build. The Windows dialogue no longer offers a RAM disk (CharonWsInstall2.h:926-950);
ramdisk::WindowsFromMicrosoft is no longer called. The ISO-in-memory start for Linux images is unchanged.
A by-product worth knowing: on firmware like VMware's, an ISO started from memory is invisible to ANY operating
system, because the firmware never publishes it; Publish() would fix that for Linux images. Not wired in (untested).


3. Windows without a stick: the temporary partition (implemented)
-----------------------------------------------------------------
New: src/efi/CharonWsWinPart.h. Flow (express and detailed modes; "I will install it myself" keeps the stick):
  - no media found -> "without a USB stick" is the first choice (CharonWsInstall2.h:926-950); only the image's address
    is settled then (winusb::ResolveAddress, CharonWsWinUsb.h:276), nothing is written;
  - questions, disk mode, target, the plan, the typed YES;
  - RunWindows (CharonWsInstall2.h:738) calls winpart::Prepare (CharonWsWinPart.h:247): winusb::Make learns the
    image's size and calls winpart::Provide (:102), which says the exact sizes and makes the partition:
      whole disk: new GPT written by Charon - EFI system partition (300 MB or more), Microsoft reserved (16 MB),
        Windows, and "Charon Windows media" (FAT32, image + Charon + 700 MB) at the end; Charon is copied to the new
        EFI partition AT ONCE, with its firmware entries, and with answers\ and plan\ when the disk was its own
        (images::CharonOnto(esp,true)); the answer file then installs into partition 3 and does not wipe the disk;
      free space / replace a partition: only the media partition is added, at the end of the largest gap;
      too little room: said with the three numbers (image, partition, available), nothing changed;
  - the image is streamed onto the partition exactly as onto a stick (split WIM), then RunWindows writes what it
    writes to a stick: Autounattend.xml (also \sources\Autounattend.xml, 1.6), NVDA for Setup, \charon, voice.conf,
    and \charon\Charon-MediaCleanup.ps1 (embedded in Charon, CharonWsWinPart.h:208);
  - first sign-in: the usual commands run from the partition (it has a drive letter), then
    "Charon-MediaCleanup.ps1 -Guid <partition GUID>" from ProgramData removes the partition and extends C:; when
    Setup put a recovery partition behind C:, it is moved to the end (reagentc /disable, remove, extend, new
    recovery partition, reagentc /enable - the sequence Microsoft documents for resizing the recovery partition);
  - a failure after the partition was added removes its entry again (winpart::Undo, :43) and says so; the closing
    sentence no longer claims "nothing changed on the target disk" when the table was rewritten
    (CharonWsInstall2.h:1039);
  - a media partition left by an earlier attempt (found by its GPT name on a fixed disk) is used again without a
    download and is never treated as a stick (winpart::IsLeftover, Prepare; CharonWsInstall2.h:916). Without this,
    a second attempt in "whole disk" mode would have written an answer file that makes Setup wipe the disk it is
    running from - found during the trials below.
  - the same helper gives the Ubuntu installer a place for its answers when the computer has no FAT volume
    (install::SeedPartition, CharonWsWinPart.h:301; section 5).
The answer file is the stick's, with three conditional additions that leave every existing golden file unchanged:
the cleanup command (key "wmediaguid"), the carry command (key "wcarry", section 5), and nothing else.

4. Install-Charon.ps1 -Mode Manager: "Reading variable BootOrder failed (error 1314)"
--------------------------------------------------------------------------------------
Reported by the Windows profiles agent on three installations (builds 26300, Server 2025, Tiny11 26200).
Read in the script: the privilege SeSystemEnvironmentPrivilege was enabled once (Enable-FirmwarePrivilege), DriverOrder
was read, then Confirm-SecureBootUEFI was called, then BootOrder was read and failed. The call order is the same
in the r408 release copy (work/charon-release-r408-install/.../Install-Charon.ps1:355, :500), so this is not a
regression of the plan agent's -PlanResult parameters. Explanation acted on: Confirm-SecureBootUEFI adjusts the
same privilege and leaves it disabled when it returns. NOT PROVEN as the cause: this host session is not
elevated (AdjustTokenPrivileges gave 1300 here), and the unfixed script was not run on my machine.
Change: Get-Var and Set-Var enable the privilege before every firmware call (Install-Charon.ps1:236-244, :257;
Install-CharonAddon.ps1:129, :142). Both scripts parse (PowerShell 5.1, 0 errors).
RAN AND PASSED (trial 3, build 26100): at the first logon and again by hand from an elevated prompt the script
installed Boot0003 "Charon" and Driver0000 with no error; -PlanResult done -PlanStep 1 -PlanText ok wrote
\EFI\HAK\plan\step1.done ("ok") and returned 0. NOT VERIFIED: on the three builds where it had failed.
Found on the way, for the plan agent: -PlanResult fails ("the EFI system partition could not be mounted", exit 1)
when the EFI partition already has a drive letter - mountvol X: /S does not give it a second one.
The coordinator's other three points:
  (a) Narrator and NVDA both on the UAC prompt: NOT REPRODUCED, NOT FIXED. After the first logon both registry lists
      held only nvda_nvda_v1 and Narrator was not running. A Narrator did appear during my checks, after my own
      key presses over VNC (Windows-key combinations), so its origin is not determined. Nothing was changed.
  (b) NVDA instead of Narrator on the OOBE pages: NOT DONE. In trial 3 those pages ("Just a moment", "Good things
      coming your way", "Getting things ready for you") need no input and lasted about two minutes. Starting a
      portable NVDA there needs it unpacked on the Windows drive in the specialize pass and registered under
      Accessibility\ATs for the system desktop; that was not tried - each attempt costs one whole installation.
  (c) the announcement of the silent minutes IS spoken before Setup starts (transcript, 14:52), and the silence was
      two minutes in trial 3.

6. The coordinator's four findings
----------------------------------
6.1 The Debian installer stopped at "Configuring keyboard-configuration - Keyboard layout:". The question is
    keyboard-configuration/variant, asked by the package's config script inside the new system (1.11). The preseed
