CHARON DRIVER PACK (r407)
=========================
Written 2026-11-22. Pack: work/charon-drivers-r407 (the r400 pack is untouched).
Regenerate: tools/make-charon-driverpack.py (fetch, ipxe, edk2, assemble, verify).
A second pack with more network drivers (newer Intel, server cards, Wi-Fi, experimental
Realtek) is made by tools/make-charon-netpack.py and described in NETWORK-DRIVERS.txt;
where that file says more about network cards than section 3 here, that file counts.
Sound: only section 5 here; codecs, amplifiers and laptops are in AUDIO-CODECS.txt.

READ THIS FIRST
  * NOTHING in this pack has been run on a physical computer.
  * The classes added in this step - input-, disk-, usb-, virt-, fs- and the folder
    manual - have NOT BEEN RUN AT ALL, not even in a virtual machine. They were built or
    downloaded, and every image was checked to be a PE32+ x86-64 UEFI driver image
    (machine 0x8664, subsystem 11 or 12) whose SHA-256 equals MANIFEST.json. That is all.
  * The network images: an earlier build of the same iPXE 2.0.0 source was run in QEMU
    (see 1.1). The images in this pack were rebuilt afterwards, no hash of the earlier
    ones was kept and iPXE puts the build time into its images, so it cannot be shown
    that these are the images that ran. Their status is also "PE header only".
    The serial logs of that run were overwritten by a failed run and deleted
    (work/r407-driverpack-evidence/NOTE.txt).
  * The loading rules of section 2 for the new classes are in src/efi/CharonDriverPack.h.
    That header compiles with the flags of the build (-Wall -Wextra -Werror) but is NOT
    YET INCLUDED by the program: until the call sites of section 7 are added, Charon
    loads only nic-*, wifi-* and net-* (CharonWsNet.h), exactly as before.

"Check" column: PE = image format and hash only. QEMU-old = PE, and an earlier build of
the same source was run in QEMU before the final rebuild (not these bytes).

2. LOADING RULES

Folder \EFI\HAK\drivers on any volume the firmware can read (Charon's stick first); a
name that occurs on several volumes is taken once; files load in name order. Every
image goes through the firmware's LoadImage and StartImage: with Secure Boot on, the
firmware refuses images it does not trust, Charon counts and reports them and goes on.
A failure is reported and never stops Charon.

2.1 nic-*.efi    (CharonWsNet.h LoadDrivers - in the program today)
    Only when the firmware drives no network adapter at all. Then all controllers are
    connected. Reason for "at all": the iPXE images open PCI I/O and USB I/O with
    EFI_OPEN_PROTOCOL_EXCLUSIVE (iPXE src/interface/efi/efi_open.c, efi_open_by_driver),
    so once they are resident, any later ConnectController on an adapter the firmware
    drives lets iPXE take it away from the firmware's driver. This is why the gap
    "the firmware drives the built-in card, a second PCI card gets no driver" is NOT
    closed: no safe rule exists with these images. For USB adapters see 2.7.
2.2 wifi-*.efi   (same place) when no adapter is driven or no Wi-Fi connection protocol.
2.3 net-*.efi    (same place) only when adapters exist without an IPv4 service.

The rules below are in CharonDriverPack.h (namespace hakefi::ws::drivers). "Nothing
drives it" means there: the handle's PCI I/O or USB I/O protocol has no BY_DRIVER,
EXCLUSIVE or BY_CHILD_CONTROLLER opener (OpenProtocolInformation); for PCI devices
also no other handle has a device path below the controller; a check that fails or
cannot be made counts as "driven". Every hardware rule works in this order:
  (1) ConnectController on the undriven handles with the drivers the firmware already
      has (fast boot leaves controllers unconnected);
  (2) only if some are still undriven, the files of the class are loaded;
  (3) ConnectController on those handles ONLY. The rules never connect all handles, so
      a pack driver is never offered a controller the firmware drives.
An image is loaded at most once: before loading, the firmware's list of loaded images
is searched for the same file path (holds across restarts of Charon in one boot). A
file that failed is not tried again in the same run; a handle is offered once per run.

2.4 fs-*.efi     LoadFileSystems()
    When a block device with a medium has neither a file system nor a partition or file
    system driver holding its Disk I/O. All fs-* load, then only those block devices
    are connected. Returns and says the number of new volumes.
2.5 disk-*.efi   LoadDisks()
    When a PCI device of class 01 (mass storage) or 08/05 (SD host controller) has no
    driver. A SECOND STORAGE DRIVER ON A CONTROLLER THE FIRMWARE DRIVES CAN DESTROY DATA
    (two drivers issuing commands to one disk); the rule exists to make that impossible:
    disk-* is not even loaded while every storage controller has a driver.
2.6 usb-*.efi    LoadUsbControllers()
    When a UHCI, EHCI or xHCI controller (0c/03/00, 20, 30) has no driver, carries no
    USB host controller protocol, and the firmware does not own it through USB legacy
    support (xHCI and EHCI: "HC BIOS owned" bit of USBLEGSUP; UHCI: SMI enable in
    LEGSUP). A second driver on a running controller would reset it: the keyboard and
    the stick Charon started from would vanish. OHCI has no driver.
2.7 nic-usb-*.efi  LoadUsbNetwork()
    When a USB interface that these six drivers bind (CDC-ECM, CDC-NCM, RNDIS, the ASIX
    IDs) has no driver and no Simple Network protocol - also while the firmware drives
    another adapter. Safe because these edk2 drivers open USB I/O BY_DRIVER without
    EXCLUSIVE. This closes the gap of 2.1 for USB adapters and phone tethering only.
2.8 input-*.efi  LoadInput()
    When a USB HID boot keyboard or mouse interface has no driver and carries no text
    input or pointer protocol. Residual risk, stated plainly: a firmware that polls USB
    keyboards outside the UEFI driver model and publishes its text input on another
    handle would look "undriven"; none is known, none was tested.
    virt-*.efi   LoadVirtual(): when a virtio device (1af4:1000-107f), VMware PVSCSI
    (15ad:07c0) or an LSI 53C895A / Fusion-MPT with the subsystem vendor of QEMU or
    VMware (never a real LSI card) has no driver.
    LoadHardware() runs usb, disk, virt, input, nic-usb in that order (each step can
    make devices for the next); LoadStorage() runs usb, disk, virt and then fs.
2.9 manual\*.efi   ManualRefresh(), ManualName(i), LoadManual(i)
    Never by a rule. The user picks a file; after it starts, all controllers are
    connected (as the UEFI Shell's "load" does). For drivers whose binding cannot be
    predicted from outside (2.10) or that duplicate a driver loaded by rule.
2.10 audio-*.efi   RESERVED. Nothing loads it; see section 5.

Why PS/2 is in manual: edk2's Ps2KeyboardDxe binds only a handle that has the Super I/O
protocol (EFI_SIO_PROTOCOL) and ends in the ACPI node PNP0303. On PC firmware nothing
publishes such a handle in a form another driver may open. SioBusDxe (written for
QEMU) makes one by binding a PCI-ISA bridge (class 06/01) that no driver manages, and
assumes the fixed ports 60h/64h. On a real PC the bridge is normally held by the
maker's chipset driver (then SioBusDxe cannot bind and nothing happens); where it is
free, the keyboard controller is usually already polled by firmware code outside the
driver model, and a second driver resetting it could take the working keyboard away.
So: honest answer, PS/2 cannot be added safely on arbitrary firmware; the three files
are there for someone who knows the machine. (Internal laptop keyboards are PS/2
devices behind the embedded controller; the firmware drives them, its setup needs them.)

Sound: see section 5 and AUDIO-CODECS.txt.


4. ADDING A MAKER'S DRIVER BY HAND

  1. Get the UEFI driver from the maker of the device or of the computer, never from
     driver collections or firmware dumps: the x64 version ("X64", "EFIx64"), a file
     ending in .efi. Known places for network cards:
       Realtek PCIe (RTL8111/8125/8126/8127): realtek.com, "PCIe FE / GBE / 2.5G /
         Gaming Ethernet Family Controller Software", UEFI, "UEFI UNDI Driver".
       Realtek USB (RTL8152/8153/8156): realtek.com, "USB FE / GbE / 2.5GbE ... Family
         Controller Software", UEFI.
       Intel: intel.com, "Intel Ethernet Connections Boot Utility, Preboot Images, and
         EFI Drivers" (PREBOOT.zip), x64 .efi files; its readme says which is for which.
     (File and folder names inside the makers' archives were not checked here.)
  2. Rename it so that the beginning of the name says what it is, and the end is .efi:
       nic-      wired or USB network card           (loaded when no adapter is driven)
       wifi-     Wi-Fi
       disk-     storage controller, RAID, card reader (loaded when a storage controller
                 has no driver)
       usb-      USB host controller
       input-    USB keyboard or mouse
       fs-       file system
     Example: nic-05-rtkundi.efi. Files load in name order; a low number goes first.
     A driver that fits none of these, or that you want to decide about yourself: put it
     into the sub-folder manual under any name ending in .efi.
  3. Copy it to \EFI\HAK\drivers on Charon's stick or on any FAT volume of the computer
     (create the folder if needed).
  4. Network: Workspace, Network; Charon loads the drivers when no card works, L loads
     again and says how many were loaded or failed. The other classes: after the call
     sites of section 7 are in the program.
  Secure Boot: with Secure Boot on, the firmware refuses every driver that is not
  signed with a key it trusts. Makers' drivers are usually signed with the Microsoft
  UEFI CA key; in this pack only fs-10-ntfs.efi is signed (Microsoft Corporation UEFI CA
  2011, which some computers - "Secured-core" - do not trust until it is allowed in
  setup). Everything else in the pack needs Secure Boot off, or your own key enrolled
  and the files signed with it.
  A maker's UNDI network driver needs the firmware's SnpDxe on top; when the firmware
  lacks it, net-11-SnpDxe.efi of the pack provides it together with the other net-*.


5. SOUND   (short; codecs, amplifiers, laptops: AUDIO-CODECS.txt)

Charon speaks through EFI\HAK\AudioDxe.efi (OpenCore AudioDxe, BSD-3-Clause, with
Charon's stream extension) and its built-in AC'97, ES1371 and USB Audio Class outputs.
Searched for further loadable UEFI sound DRIVERS (edk2, edk2-platforms, edk2-staging,
Project Mu, OpenCore/Acidanthera, coreboot based edk2 forks, GitHub); result:
  Intel SOF / cAVS / SoundWire DSP   none exists
  AMD ACP                            none exists
  USB Audio Class 1/2/3              no driver. Goldfish64/AudioPkg has an unfinished
                                     UsbAudioController (archived 2020, installs no audio
                                     protocol). edk2's XhciDxe and EhciDxe return
                                     EFI_UNSUPPORTED for isochronous transfers, which is
                                     why a class driver on top of them cannot play.
                                     Charon's own output (CharonUsbAudio.h) drives the
                                     isochronous endpoint itself, beside the xHCI driver.
  virtio-snd                         none exists (not in OvmfPkg)
  HDMI / DisplayPort                 no separate driver; AudioDxe sees the digital pins,
                                     real output unconfirmed (AUDIO-CODECS.txt)
  Bluetooth                          none (no Bluetooth stack, section 3)
  Another HD Audio driver            ethindp/edk2, branch audio-output-protocol: an
                                     HdaAudioDxe with its own audio output protocol,
                                     BSD-2-Clause-Patent, not upstream, analog only,
                                     unknown whether it works. It covers the hardware
                                     AudioDxe covers and does not speak Charon's stream
                                     protocol: not taken.
The UEFI specification defines no audio protocol. So the pack contains no sound driver
and the class audio-*.efi stays reserved: a driver would be usable only if it offered
Charon's stream protocol (HAKAudioStream.h), and none does.


6. HOW THE FILES WERE MADE

6.1 iPXE (nic-10..40): iPXE publishes no driver images. tools/make-charon-driverpack.py
  ipxe boots the official Alpine Linux 3.24.4 "virt" ISO (SHA-256 pinned) in a throw-away
  QEMU machine, installs gcc from Alpine's repository, builds the pinned iPXE 2.0.0
  source into *.efidrv groups and hands them back as a tar archive on a raw disk; the
  machine is deleted. Changes (in source/ipxe-build): config/local/usb.h links no host
  controller, USB disk or keyboard driver and no EFI_USB_IO provider, only "usbio", the
  client of the firmware's USB stack; ipxe-usb.patch lets the USB core try the other
  configurations a driver accepts and limits the interrupt polling interval to 255 ms.
6.2 edk2 and OpenCore (nic-usb-*, input-*, disk-*, usb-*, virt-*, fs-20, seven files in manual):
  built with MSVC in the edk2 (AUDK) workspace work/ha, RELEASE, by the stage "edk2".
  The workspace is not a git checkout, so no commit can be named: the pack carries a copy
  of every compiled module folder and MANIFEST.json the SHA-256 of every file in it.
  ASIX: edk2-platforms commit 4db2845d, every file SHA-256 pinned. Two additions for
  loading on any firmware (source/edk2/CharonDriverPkg): UefiStallTimerLib, a TimerLib
  on the Stall() boot service and the time stamp counter (edk2's instances need a
  platform; AtaAtapiPassThru, AtaBusDxe, UfsPassThruDxe, XhciDxe, Ps2KeyboardDxe use
  it), and a copy of Ext4Dxe whose only change is the package reference of one library.
  The stage takes work/ha/.charon-build.lock, writes only into its own Build folder and
  removes it. Two builds of the same sources gave different image hashes (the MSVC link is
  not bit-reproducible here); MANIFEST.json describes the images that are in the pack. NOT RUN.
6.3 Release binaries (fs-10, fs-11, fs-21..61, 21 files in manual): downloaded from the
  projects' own GitHub release pages, https://github.com/pbatard/efifs/releases/tag/v1.13
  (2026-10-08) and https://github.com/pbatard/ntfs-3g/releases/tag/1.9 (2026-06-19); the
  SHA-256 of every file equals the digest GitHub's release API reports for the asset and
  is pinned in the tool. Not rebuilt, not run on the host.
6.4 Licences: iPXE GPL-2.0-or-later (files under GPL-2.0-only, UBDL, BSD); EfiFs and GRUB
  GPL-3.0-or-later; ntfs-3g GPL-2.0-or-later (library LGPL); edk2 BSD-2-Clause-Patent;
  OpenCorePkg BSD-3-Clause.
  The GPL drivers are separate programs in separate files, loaded through the firmware
  and shipped beside Charon (aggregation). The pack carries the licence texts and the
  complete corresponding source: source/ipxe-2.0.0.tar.gz with recipe and changes,
  source/efifs-1.13.tar.gz with source/grub-f10ad08f....tar.gz (the GRUB commit the
  EfiFs release pins as its submodule; EfiFs's own patch to GRUB is in its archive),
  source/ntfs-3g-uefi-1.9.tar.gz. Not checked: that the published binaries can be
  reproduced bit for bit from those archives.
