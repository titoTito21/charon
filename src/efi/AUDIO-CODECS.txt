Charon HD Audio codec support (r408)
====================================

This file describes what the pre-boot HD Audio driver (EFI/HAK/AudioDxe.efi)
does for each codec family, where that knowledge comes from, what is not
done and why, and the licences involved. Controllers, AC'97, ES1371 and the
order in which Charon picks an output are in audio_stream/AUDIO-HARDWARE.txt.
USB sound cards are in USB-AUDIO.txt (CharonUsbAudio.h).

STATE OF THE EVIDENCE. The driver was built (AudioDxe-r408.efi) and run in
ONE QEMU machine with the emulated HD Audio card (see "What was verified").
That run proves that nothing regressed for virtual machines. NO PHYSICAL
CODEC WAS EXERCISED: everything below that names a real codec or laptop was
written from the Linux kernel sources and has never played a sound on that
hardware. Treat every per-family and per-machine statement as "implemented
from source, untested on hardware".

2. What the driver does for EVERY codec (generic bring-up)
----------------------------------------------------------

Compared with the kernel's generic parser (generic.c, auto_parser.c):

  kernel generic parser                 this driver
  ------------------------------------  ------------------------------------
  function group and widgets to D0      at probe (AudioDxe); r406: checked
                                        again and waited for before playback
  output pins from the pin default      line out, speaker, headphone, S/PDIF,
  configuration                         other digital out (AudioDxe)
  speaker/headphone pins with           r408: accepted (association set to
  association 0 are outputs             15 in the driver's copy); AudioDxe
                                        ignored them
  pin widget control OUT, HP for        OUT (AudioDxe); HP_EN on headphone
  headphone pins                        pins with a headphone amplifier (r406)
  path pin -> (mixer/selector) -> DAC,  first DAC found depth-first; every
  one DAC per output                    output gets the same stream (speech
                                        is sent to all outputs at once)
  connection selects on the path        yes (AudioDxe)
  output amplifiers unmuted with a      yes, on pin, mixer/selector and DAC,
  gain, mixer input unmuted             gain from the caller, clamped to the
                                        amplifier's range (AudioDxe)
  EAPD on                               on every pin with the capability,
                                        not only the pins played to (r406)
  44.1 kHz / 48 kHz families            both, taken from the DAC's or the
                                        function group's capabilities
  several codecs on one link            one device per codec; Charon tries a
                                        codec with analog outputs first
  automatic muting on headphone plug,   NOT done, on purpose: a blind user
  jack detection, volume keys           hears speech on every output
  microphones, recording, more than     not done
  two channels, surround, S/PDIF
  status bits, HDMI channel maps/ELD

A codec that no table knows (unknown vendors, future IDs) gets exactly this
and nothing else.

4. Machine quirks (r408, generated table)
-----------------------------------------

Charon carries the kernel's subsystem-ID quirk lists as DATA. The table
audio_stream/driver/HakHdaQuirkTable.h is generated by

    python3 -I tools/gen-charon-hda-quirks.py <linux tree> \
        src/efi/audio_stream/driver/HakHdaQuirkTable.h --tag v7.3 --commit <sha>

from kernel v7.3. The generated header records the kernel tag and commit,
every input file with its SHA-256 and licence, and the list of function
fixups that were not ported. The generator refuses any input file that is
not GPL-2.0-or-later.

What is imported: for 31 fixup tables (the nine Realtek drivers; Conexant
5045/5047/5051/5066; Senary SN6186; Cirrus CS420x, CS4208, CS421x; ten
IDT/SigmaTel sub-families; VIA VT2002P/VT1802; Analog Devices AD1986A,
AD1981, AD1884) the codec IDs the kernel driver binds to, the subsystem-ID
rows in the kernel's order, and of the fixups those rows reach: pin
configuration lists (HDA_FIXUP_PINS), verb lists (HDA_FIXUP_VERBS), pin
control lists (HDA_FIXUP_PINCTLS) and their chains.

    subsystem-ID rows imported                    1897
    rows whose chain contains at least one
      action this driver performs                 1128
    fixups kept                                    493
      pin configuration lists                      252
      verb lists                                    58
    by subsystem vendor (rows / with an action):
      Dell 1028    215 / 183      HP 103c      604 / 133
      ASUS 1043    211 / 141      Lenovo 17aa  243 / 179

"With an action" does not mean "speakers fixed": most pin lists of recent
laptops describe a headset microphone, which Charon does not use. The rows
without an action are kept so that the first-match order is the kernel's.

Matching is the kernel's (auto_parser.c snd_hda_pick_fixup): each row
against the PCI subsystem ID of the controller (rows written with
HDA_CODEC_QUIRK against the codec's subsystem ID), then all rows against the
codec subsystem ID; a table is consulted only for the codec IDs (and
revisions) of its kernel driver. Pin overrides are applied to the driver's
copy of the pin configuration before the outputs are chosen; the codec's
own pin defaults are never written. Verb lists are sent after the output
paths are up, as the kernel does at init.

5. Safety rules and the off-switch
----------------------------------

  * Virtual machines: nothing of r408 runs for a QEMU codec (vendor 1af4), a
    VMware codec (vendor 15ad), or on any machine whose processor reports a
    hypervisor (CPUID leaf 1, ECX bit 31). There the driver behaves as r407.
  * Vendor verbs (Realtek coefficients on node 0x20, the IDT verb 7E7) are
    sent only to codecs whose ID the kernel lists for them. Machine verb
    lists are sent only when codec ID AND subsystem ID match, and only to
    nodes the codec has.
  * GPIOs outside the mask of a fixup keep the firmware's state.
  * The codec's pin defaults, which survive a reset, are never written.
  * Nothing in the quirk code returns an error to the playback path.
  * OFF-SWITCH: create an empty file \EFI\HAK\audio-noquirks on any file
    system the firmware has connected (the Charon stick is enough). The
    driver looks for it once, when the first codec is bound; with the file
    present it does only the generic bring-up of section 2 without the
    association-0 rule (that is: r407 behaviour). A build with
    HAK_HDA_NO_QUIRKS defined (set "_CL_=/DHAK_HDA_NO_QUIRKS" as
    build-host-baseline.cmd does for HAK_AUDIO_TRACE) has the switch
    permanently off.
  * A trace build (HAK_AUDIO_TRACE=1) prints on COM1 the codec ID, both
    subsystem IDs, the matched table row, every pin override and GPIO write.


6. Smart amplifiers, SoundWire, SOF, AMD ACP
--------------------------------------------

Nothing of this section is implemented. The facts were read in the kernel
tree named in section 1; "not verified" marks what was not.

Smart amplifiers beside an HD Audio codec (Lenovo Legion/Yoga/ThinkPad,
ASUS ROG/Zenbook, HP, Dell XPS; about 320 of the 1236 rows of the ALC269
table):
  * Cirrus CS35L41 (ACPI CSC3551, CLSA0100, CLSA0101). The Realtek codec
    sends I2S to the amplifiers; they are controlled over I2C or SPI.
    cs35l41_hda.c contains a complete path WITHOUT DSP firmware:
    cs35l41_hda_config[] (PLL from the 3.072 MHz bit clock, 48 kHz, 32-bit
    I2S slots) plus cs35l41_hda_config_no_dsp[] ("DACPCM1_SRC = ASPRX1"),
    cs35l41_hda_unmute[] and the amplifier enable bit; the driver itself
    uses it ("Bypassing Firmware.") when the SPI bus is too slow for a
    download. That is roughly 25 register writes per amplifier, plus the
    revision errata sequence and the boost set-up (cs35l41_init_boost in
    sound/soc/codecs/cs35l41-lib.c, not in the checkout, not verified).
    What a UEFI driver needs: (1) an I2C host driver for the SoC's Synopsys
    DesignWare controller (Intel LPSS, AMD AMDI0010) or an SPI host driver;
    (2) the amplifier's bus address, reset GPIO, boost type (internal /
    external / shared), inductor, capacitor and peak current: from ACPI
    _DSD ("cirrus,dev-index", "cirrus,boost-peak-milliamp",
    "cirrus,boost-ind-nanohenry", "cirrus,boost-cap-microfarad",
    "cirrus,gpio1-func" ..., "reset" GPIO), which needs an AML reader, or
    from the kernel's table for machines whose ACPI lacks them
    (cs35l41_hda_property.c); (3) a driver for the SoC GPIO block that holds
    the reset line. Risk: the boost parameters are electrical; a wrong
    inductor/current setting on an external-boost design can overheat the
    converter, and without the speaker-protection firmware nothing limits
    excursion and temperature: a UEFI path must play at a low fixed gain.
    Licence: every cs35l41_hda*.c file is GPL-2.0-only, so a port needs the
    project to accept GPL-2.0-only for that driver or a clean
    implementation from the datasheet. Firmware (not needed for the
    no-DSP path): linux-firmware WHENCE "License: Redistributable. See
    LICENSE.cirrus for details." (the licence text itself was not read).
  * Cirrus CS35L56/CS35L57 (cs35l56_hda.c, GPL-2.0-only). The chip runs
    firmware from ROM; the kernel says "If the BIOS didn't patch the
    firmware a wmfw and bin file are mandatory": on these laptops the
    vendor firmware may already have patched and configured the amplifier
    before Charon starts. Whether sound then passes with only the codec
    side enabled was not verified and is the first thing to try on such a
    machine: it costs nothing.
  * Texas Instruments TAS2781/TAS2563 (tas2781_hda_i2c.c, _spi.c,
    GPL-2.0-only; ACPI TIAS2781, TXNW2781, INT8866). The driver requires
    its register configuration file (TAS2XXX<ssid>.bin "RCA" profile) and
    normally a DSP program; calibration is read from UEFI variables
    ("CALI_DATA" / "SmartAmpCalibrationData", three vendor GUIDs in
    tas2781_hda.c), which a UEFI program can read directly. Firmware:
    WHENCE "Licence: Redistributable. See LICENCE.ti-tspa for details"
    (text not read). A firmware-free register sequence was not found in
    the driver; not verified whether the chip plays in its reset default.
  * Awinic AW88399 (aw88399_hda*.c, GPL-2.0-only; Legion Pro 7i 16IAX10H,
    R9000P): needs its firmware profile; not examined further.
  * Headphones on all of these machines are an ordinary pin of the Realtek
    codec (the kernel's fixups only add the amplifiers as components), so
    the generic path plus the family initialisation applies to the jack.
  * Published UEFI code for any of these amplifiers: none known to this
    pass; coreboot/depthcharge were not searched (see section 1).

Concrete plan for CS35L41, smallest useful step first:
  1. Read-only probe: find the DesignWare I2C controllers (PCI class 0C/80
     Intel LPSS IDs, or ACPI AMDI0010/80860F41... through EFI_ACPI_SDT),
     read the CS35L41 device ID register at the addresses 0x40-0x43, and
     report it in Charon's hardware inventory. No writes to the amplifier.
  2. Decide the licence question (GPL-2.0-only port or datasheet rewrite).
  3. Bring-up for INTERNAL-boost designs only, parameters from _DSD or the
     property table, fixed low gain, behind an explicit user opt-in, on one
     known laptop at a time.

Machines without any HD Audio codec:
  * Intel SoundWire (RT711/RT712/RT713/RT722 jack codecs, RT1316/RT1318,
    CS35L56, CS42L43 amplifiers; Tiger Lake and newer, most 2023+ Dell XPS /
    Latitude and many ThinkPads). In the kernel the SoundWire data ports are
    DAIs of the SOF driver: sound/soc/sof/intel/hda-dai.c
    sdw_hda_dai_hw_params() configures an IPC4 "copier" in the DSP
    firmware. So playback needs the DSP firmware image (sof-*.ri, signed
    for the platform) and a topology to be loaded and the IPC protocol
    spoken, besides a SoundWire bus master driver (Cadence IP), device
    enumeration and each codec's register set-up. The SOF Intel sources
    are "GPL-2.0-only OR BSD-3-Clause". Whether Lunar Lake and later can
    move SoundWire PCM with HD Audio DMA and no firmware (hda-sdw-bpt.c,
    lnl.c exist) was not verified. This is months of work, not a quirk.
  * AMD ACP (ACP 6.x/7.x with SoundWire or I2S codecs). The tree has a
    "legacy" (non-SOF) machine path beside the SOF one
    (sound/soc/amd/acp/acp-sdw-legacy-mach.c, acp-legacy-common.c), which
    suggests PCM without DSP firmware is possible there; not verified.
    Firmware for the SOF path: WHENCE "Licence: Redistributable. See
    LICENSE.amdsof for details."
  * Until then such machines speak through a USB sound card or headset
    (USB-AUDIO.txt). The HD Audio driver recognises a link without codecs
    and releases the controller (r406).

  HakHdaQuirks.[ch], HakHdaQuirkMatch.h,    GPL-2.0-or-later (logic and data from

  AudioDxe-r408.efi links all of them, so the binary as a whole is

  sources. A release that ships AudioDxe-r408.efi must say so and offer the
  sources of the driver (this directory, the generator, the pinned OpenCore
  tree), as Charon already does for its own GPL parts. r407 and earlier
  were MIT/BSD-only.
